# Архітектура

## Шлях даних

```
текст програми
   │  parser.parse_tree()        Lark LALR(1) за grammar/sipl.lark
   ▼
ParseNode                        дерево виводу: кожна лексема і кожне правило, з SourceSpan
   │  parser.build_ast()         згортання: зникають дужки, ключові слова, ланцюжки expr→term→factor
   ▼
ast.Program                      типізоване AST, кожен вузол зі SourceSpan
   │  Interpreter(...).events()  ледачий потік подій
   ▼
Event, …, Finished               BeforeStatement / VariableChanged / ConditionEvaluated / AfterStatement
```

Збоку від цього шляху:

- `diagnostics.Diagnostic` — єдиний формат помилок для парсера й інтерпретатора.
- `visualization.VisNode` — спільна модель дерева; у неї перетворюються і `ParseNode`, і AST,
  тому кожен формат експорту написано один раз.
- `cli` — тонка обгортка: лише розбирає аргументи, викликає функції бібліотеки та друкує результат.

## Модулі

| Модуль | Відповідальність | Залежить від |
| --- | --- | --- |
| `ast` | вузли AST, `SourceSpan`, `to_dict` | — |
| `diagnostics` | `Diagnostic`, коди помилок, винятки | `ast` |
| `parse_tree` | `ParseNode` | `ast` |
| `parser` | текст → `ParseNode` → AST; діагностика синтаксису | Lark, усе вище |
| `interpreter.events` | типи подій | `ast`, `diagnostics` |
| `interpreter.machine` | виконання, стан, ліміт кроків | `ast`, `events` |
| `visualization` | text / JSON / DOT / SVG / HTML | `ast`, `parse_tree` |
| `cli` | командний рядок | усе |

Lark імпортується лише в `parser.py`. Жоден об'єкт Lark не виходить за межі цього модуля,
тож рушій розбору можна замінити, не зачіпаючи решти коду.

## Рішення та їх причини

**Дерево виводу й AST — окремі структури.** Дерево виводу потрібне для практичної роботи 1
(синтаксичний вивід) і зберігає кожну лексему. AST потрібне для виконання й не містить нічого
зайвого. Зв'язок між ними — `SourceSpan`: вузол AST і вузли дерева виводу, з яких він утворений,
покривають той самий фрагмент тексту. На цьому побудоване порівняння в `sipl compare`.

**Інтерпретатор — генератор подій.** `Interpreter.events()` видає події по одній і між ними стоїть
на паузі. `run` просто дочитує потік до кінця, `trace` збирає його у список, а debugger може
зупинятися на `BeforeStatement` із потрібним `span`, показувати `interpreter.state` і продовжувати
викликом `next()`. Окремого «режиму налагодження» в ядрі не потрібно.

**Помилки — дані, а не текст.** Парсер та інтерпретатор повертають `Diagnostic` з кодом і `span`.
Текст для термінала та JSON для IDE будуються з одного об'єкта.

**Точний список очікуваних лексем.** LALR-автомат устигає виконати згортки до того, як помітить
помилку, тому його власний список очікуваного буває неповним. Парсер заново програє коректний префікс
і опитує автомат безпосередньо перед помилковою лексемою (`parser._context`).

**Ключові слова розпізнає лексер.** Лексер працює без урахування контексту, тому `end` — завжди
ключове слово й ніколи не стає змінною лише через те, що в цьому місці граматика чекала змінну.

## Як підключити інший інструмент

- Через бібліотеку: `sipl.parse`, `sipl.parse_tree`, `sipl.run`, `sipl.trace`, `sipl.Interpreter`.
- Через процес: `sipl … --json`; контракт описано в [json-schema.md](json-schema.md).

VS Code extension, language server чи web playground мають викликати одне з двох і не містити
власного парсера.

## Межі

- Одна синтаксична помилка за запуск: після першої помилки розбір зупиняється.
- Зупинка за лімітом кроків не доводить, що цикл нескінченний, — лише що він не завершився за N кроків.
- Обхід дерев рекурсивний; послідовності операторів (`Seq`) розгортаються циклом, тож довгі програми
  не впираються в ліміт рекурсії, а глибоко вкладені вирази — можуть.
